# Architecture And Data Flow

## High-Level Architecture

This project is a Next.js App Router application.

- UI entrypoint: `app/page.tsx`
- Main client shell: `components/main/App.tsx`
- Root layout and external scripts: `app/layout.tsx`
- API routes: `app/api/**`
- Auth and database wiring: `server/auth.ts`

The browser owns the active editing state through `AppData`, but persistence and authenticated integrations are server-backed.

## Core Module Boundaries

- `components/main/App.tsx`
  - main client orchestrator
  - owns `AppData`
  - restores session state
  - coordinates imports, saves, exports, and modals
- `components/transmittal/TransmittalTemplate.tsx`
  - printable transmittal layout
  - editable item table and form sections used by the live preview
- `lib/auth-client.ts`
  - Better Auth client setup for browser session and OAuth actions
- `server/auth.ts`
  - Better Auth server configuration
  - Prisma client setup
  - Google OAuth provider definitions
- `services/geminiService.ts`
  - Gemini parsing logic
  - response schema
  - document-number fallback resolution
- `services/googleDriveService.ts`
  - gets Google access token from `/api/google-token`
  - Drive file metadata, download, search, folder listing, and upload
- `services/googleSheetsService.ts`
  - linked spreadsheet ID storage in `localStorage`
  - reads `Sheet1`
  - appends summary rows to `Sheet1`
- `services/docxGenerator.ts`
  - builds the DOCX export with `docx`
  - uses `services/logo-image.ts` to download a PNG rendition of a stored logo URL
- `server/imagekit.ts`
  - validates raster logo bytes, uploads to ImageKit using server-only credentials, and returns URL/file ID metadata
- `server/sender-logo.ts`
  - ensures new sender snapshots store a logo URL instead of inline image data
- `hooks/useFileProcessing.ts`
  - upload preprocessing
  - document type filtering (standalone images are disabled)
  - sequential/concurrency-limited parsing queue

## Runtime Flow

### Startup And Session

1. `app/page.tsx` renders `App`.
2. `App` uses `useSession()` from Better Auth.
3. If no session is present, the login screen is shown.
4. If a session is present:
   - Drive access is checked
   - `GET /api/transmittals/next-number` is called
   - `GET /api/agencies` is called

### Import Pipelines

#### Local Uploads

1. User selects PDF or Word files.
2. `useFileProcessing` reads the file as base64.
3. Word documents are converted to text; image imports are rejected.
4. `parseTransmittalDocument()` is called.
5. Parsed items are merged into `data.items`.
6. Parsed header fields are merged into recipient/project fields when available.

#### Google Drive File Selection

1. The app lists Drive files using the current session token.
2. Selected files are downloaded from Drive.
3. Each file is parsed with Gemini.
4. If parsing fails or the file is not analyzable, the app creates a fallback row.

#### Google Drive Folder Link

1. The folder ID is extracted from the pasted link.
2. Files in the folder are listed.
3. Each file runs through the same AI-or-fallback import path as Drive selection.

#### Google Drive Single File Link

1. The file ID is extracted from the pasted link.
2. The file metadata is loaded.
3. The file runs through the same AI-or-fallback import path as Drive selection.

#### Google Sheets Link

1. The sheet ID is extracted from the pasted link.
2. `Sheet1` is read.
3. Headers are mapped to likely item columns.
4. Rows are converted into `TransmittalItem` entries.

### Save Pipeline

#### Create

1. `POST /api/transmittals`
2. The server validates the authenticated user.
3. The server generates the next monthly transmittal number inside a transaction.
4. The server stores:
   - top-level transmittal fields
   - JSON snapshots (`project`, `sender`, `receivedBy`, `footerNotes`)
   - recipients
   - item rows
5. The response returns the saved transmittal, including the server-assigned number.
6. On create only, if a linked Google Sheet ID exists, the client appends a summary row to the sheet.

#### Update

1. `PUT /api/transmittals/[id]`
2. The server validates ownership.
3. The server validates duplicate transmittal number conflicts.
4. Existing recipients and items are replaced with the submitted set.
5. The updated transmittal is returned.

### Export Pipeline

- PDF
  - generated from an isolated clone of `#print-container` using `html2pdf.js` and `html2canvas`
  - `lib/pdf-layout.ts` lays out the clone at the actual Letter-page content width (720 CSS pixels with half-inch margins), removes the editor's page minimum height, and applies compact export spacing
  - rows fill the available page space in order, and individual sign-off sections flow after the table
  - rows and sign-off sections that fit on a full page stay intact. Oversized content can flow across pages
- Print
  - the app's Print action uses the same compact clone and lets the browser paginate the table and repeat its column headings
- DOCX
  - generated by `services/docxGenerator.ts`
- DOCX Preview
  - generates the same DOCX blob, then converts it to HTML using `mammoth`
- CSV
  - generated client-side from `data.items`
- Drive upload
  - uploads the generated blob to a selected Drive folder

## Parsing And Document-Number Fallback

`services/geminiService.ts` is responsible for parsing documents and normalizing document numbers.

The parsing route now uses a local-first pipeline:

1. For PDFs, `server/pdf-parsing.ts` classifies the PDF and extracts cover-page Markdown with PDF Inspector. When the cover is scanned, sparse, or broken-font, it runs local OCR (`server/ocr.ts`) on the cover plus flagged pages up to `OCR_PARSE_MAX_PAGES` (default 3). Usable OCR text takes the text path (`readMethod: "ocr"`). Otherwise the original PDF goes to Gemini visually with a reason (`ocr_unavailable`, `ocr_timeout`, `scan_unreadable`, or `extraction_failed`).
2. `server/local-document-parser.ts` accepts only a descriptive labelled title and explicit numbered identifier. It returns one item and any explicitly labelled header fields without querying AI settings or invoking Gemini. Uncertain fields are left empty rather than invented.
3. When local metadata is insufficient, Gemini interprets reliable extracted text. Scanned or unreliable PDF covers use Gemini's visual input. Word text is also treated as a single document; bulk text lists use a distinct multi-item prompt.
4. Gemini output must contain a usable description, is normalized to string fields, and is restricted to one item for document imports. Header fields are whitelisted. Explicit identifier prefixes such as `INV-12345` are preserved.
5. Missing keys, timeouts, empty or invalid AI output, and service errors produce filename-based fallback items marked `readMethod: "none"`, each with exactly one `reason` from `lib/parse-reasons.ts`. Raw provider messages are never returned or logged. For unreadable rows with generic file names (`scan.pdf`, `IMG_0001.pdf`), the document number stays empty instead of being invented. Bulk text lists retain their line-based fallback.
6. Responses identify the parser as `pdf-inspector`, `gemini-text`, `gemini-visual`, or `fallback`, plus `readMethod` (`text`, `ocr`, `visual`, `none`), an optional `reason`, and `keyClass` (`user`, `system`, `none`). When a stored personal key cannot be decrypted, the response carries `personalKeyStatus: "unusable"` and the system key is used. Timings include authentication, native extraction, AI settings, and interpretation.
7. When a text PDF's cover has no strong identifier, pages 2–3 are read once natively. A labelled identifier found there replaces the weak number. Otherwise the result carries `document_number_unresolved`.
8. A visual PDF over `GEMINI_INLINE_MAX_BYTES` decoded bytes (default 20 MB, below the 25 MB encoded request cap) or 1,000 pages is refused with `too_large` before any provider call.

Gemini's request timeout is 60 seconds, reduced by time already spent in the route (minimum 20 s), so the 90-second browser timeout is not exceeded. When it is, the client reports `provider_timeout` ("The document took too long to analyze"). The `document_parse_complete` log records `flow`, `readMethod`, `reason`, `keyClass`, page and OCR counts, and timings. It never records document text, file names, or keys. Import rows carry a session-only `extraction` marker, and the Files panel lists rows that need review. The marker is not persisted.

### Local OCR runtime

PDF Inspector's OCR (`processPdfWithOcr`, `Auto` mode, `offline: true`) needs PDFium, ONNX Runtime, and the PP-OCRv6 Small model set. `scripts/fetch-ocr-runtime.sh` downloads checksum-pinned builds into `vendor/ocr/` (gitignored), warms the models once, and keeps only the three model files as a read-only `modelDirectory`. `next.config.mjs` traces `vendor/ocr/**` into the parse and QA routes. The script runs from `vercel-build` and only does work when `OCR_BUNDLE_RUNTIME=true`. Locally, `npm run ocr:runtime` provisions linux-x64 or mac-arm64 (the latter is "preview" upstream).

| Variable | Default | Effect |
| --- | --- | --- |
| `OCR_BUNDLE_RUNTIME` | unset | `true` makes the build download and bundle the runtime (about 65 MB unzipped). |
| `OCR_ENABLED` | unset (off) | `true` lets requests run OCR when the runtime is present. Otherwise the result is `ocr_unavailable` and the Gemini visual path runs. |
| `OCR_PARSE_MAX_PAGES` / `OCR_QA_MAX_PAGES` | 3 / 10 | Page caps per request. |
| `OCR_TIME_BUDGET_MS` | 45000 | Response budget for OCR. The native call cannot be cancelled. A late result still fills the cache. |
| `OCR_RUNTIME_DIR` | `vendor/ocr` | Runtime location override. |

OCR results are cached in-process by SHA-256 of the PDF bytes (32 documents, 64 MB of text, 30 minutes). Concurrent identical requests share one native call. The cache is per instance and is not shared across instances.

**Rollout and recovery.** Ship with `OCR_ENABLED=false` first, so reason codes and review markers are live without OCR. Enable it on a preview after measuring function size and cold start, then on production. To disable, set `OCR_ENABLED=false` and redeploy the same build (Vercel applies env changes on redeploy). Requests then use Gemini visual reading with an `ocr_unavailable` reason.

## API Surface

### Authenticated Routes

- `GET /api/transmittals`
  - auth required
  - returns all transmittals for the current user
  - includes items, recipients, and agency
- `POST /api/transmittals`
  - auth required
  - accepts `{ data }` where `data` follows the `AppData` shape
  - creates a new transmittal and assigns the next monthly transmittal number
- `PUT /api/transmittals/[id]`
  - auth required
  - accepts `{ data }`
  - updates a transmittal owned by the current user
- `DELETE /api/transmittals/[id]`
  - auth required
  - deletes a transmittal owned by the current user
- `GET /api/transmittals/next-number`
  - auth required
  - returns the next available transmittal number for the current month
- `GET /api/agencies`
  - auth required
  - returns the shared agency library with `canManage` permissions for the current user
- `POST /api/agencies`
  - auth required
  - accepts `{ agency }`
  - uploads a pending logo to ImageKit, then creates an agency with `logoUrl` and `logoFileId`
  - duplicate creator/name pairs are rejected instead of silently replacing an existing record
- `PUT /api/agencies/[id]`
  - auth required
  - accepts `{ agency }`
  - updates a saved agency owned by the current user
- `DELETE /api/agencies/[id]`
  - auth required
  - deletes a saved agency owned by the current user
- `GET /api/google-token`
  - auth required
  - returns the current Google access token for the linked account
  - may refresh the token server-side before returning it

### Other Routes

- `POST /api/parse-transmittal`
  - no explicit auth check in the route
  - accepts `content`, `mimeType`, `isText`, and optional `fileName`
  - returns parsed items/header or an error
- `GET /api/export-transmittals`
  - token-protected with `SEND_API_TOKEN`
  - returns flattened export rows across transmittals
  - accepts the token from `x-api-token` or the `token` query param
- `/api/auth/[...all]`
  - Better Auth handler for sign-in, callback, session, and sign-out flows

## Core Client Types

These types are defined in `types.ts` and shape the live editing state:

- `AppData`
- `TransmittalItem`
- `RecipientInfo`
- `ProjectInfo`
- `SenderInfo`
- `Signatories`
- `ReceivedBy`
- `FooterNotes`

`AppData` is the client-side source of truth while editing. It is serialized and sent to the server when saving.

## Persistence Model

The main Prisma models are:

- `Transmittal`
  - parent record for one saved form
  - stores structured JSON snapshots plus top-level searchable fields
- `Recipient`
  - recipient rows related to a transmittal
- `TransmittalItem`
  - item rows related to a transmittal
- `Agency`
  - shared sender/branding record with a creator
  - stores the ImageKit delivery URL and file ID; the legacy inline-logo column is cleared on migration or save

Better Auth also uses:

- `User`
- `Account`
- `Session`
- `Verification`

## Important Note About Older Documentation

Some older docs and notes describe the app as a browser-only SPA with local history snapshots. That is no longer the active architecture.

The current implementation uses database-backed transmittals and agencies. `localStorage` is only used for lightweight local values such as the linked Google Sheet ID.
